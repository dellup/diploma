**Заказчик разработки:** Nexign BSS.

## Введение. Почему я выбрал эту тему

Nexign Data Integrator (DIP) — платформа для сбора, преобразования и передачи данных между корпоративными системами. Обработка в ней описывается сценарием, который собирают в визуальном редакторе из операторов: одни читают данные, другие изменяют их структуру, третьи передают результат. Такой подход позволяет повторно использовать готовые операции при создании разных интеграций. В платформе также предусмотрены репликация данных и мониторинг [6]. HTTP-часть модуля ESB связывает сценарии DIP с запросами внешних приложений: принимает запрос, передаёт его на обработку и возвращает ответ. Поэтому модуль разрабатывается с учётом уже существующих операторов и механизма исполнения сценариев.

Тема связана с моей работой: я участвовал в разработке модуля ESB для Nexign Data Integrator. В дипломе хочу разобрать HTTP-часть этого модуля: как запрос внешней системы попадает в сценарий DIP, где проверяются и преобразуются данные и как формируется ответ.

Заказчиком разработки выступает Nexign BSS. Модуль должен упростить подключение систем с разными интерфейсами и изменение интеграций, используя существующие сценарии DIP [6].

### Зачем нужен модуль ESB

Для HTTP-интерфейса нужно разобрать запрос, проверить данные, вызвать обработку и вернуть ответ. При создании других интеграций эти операции повторяются, а разрозненные правила ошибок и преобразований усложняют сопровождение. Проблема рассматривается в работах об интеграционных шаблонах и сервисных архитектурах [3, 8].

В модуле общие операции вынесены в операторы Data Integrator. API описывается в OpenAPI/YAML, обработка выполняется сценарием DIP, а преобразование сообщения задаётся выражением. При добавлении метода разработчик повторно использует механизмы приёма запроса, проверки и ответа.

Ожидаемый результат — снизить затраты на интеграции и сократить время доставки изменений. Например, при переименовании поля могут потребоваться правки контракта и преобразования при сохранении общего кода HTTP-обработки. В каких случаях достаточно изменить настройки, я проверю в эксперименте.

В дипломе рассматривается HTTP-подсистема ESB внутри существующей платформы DIP. Её задача — связать HTTP-взаимодействие с моделью сценариев, операторов и пакетов данных.

### Пример взаимодействия систем

Для объяснения возьму учебный пример из области BSS: CRM запрашивает список услуг клиента у биллинга. 

> GET /customers/1001/services?status=active&status=suspended

HTTP Server принимает запрос. Gateway находит в описании API операцию получения услуг, извлекает идентификатор клиента из пути и проверяет параметры. Два значения status должны сохраниться как список. Затем запрос передаётся в сценарий, который начинается с HTTP Function Start.

Сценарий получает данные у целевой системы с помощью подходящих операторов DIP. Если биллинг возвращает поле service_code, а CRM ожидает поле code, преобразование задаётся отдельно от способа приёма запроса. HTTP Response собирает результат, кодирует его в выбранный формат и возвращает клиенту. При ошибке должны быть определены HTTP-статус, структура сообщения и нужные заголовки.

В примере контракт задаёт интерфейс, сценарий выполняет обработку, преобразование согласует данные, а HTTP-операторы обеспечивают обмен. Этот путь запроса я прослежу в реализации.

| Ошибки HTTP Server | Настройка шаблонов ответов сервера                                                                           |

| Преобразование структуры | Отображение полей, объектов и массивов через JSONata; использование Groovy для скриптовой обработки          |

### Выводы по обзору

Из рассмотренных работ я беру несколько решений. Первое — разделение приёма сообщения, маршрутизации, преобразования и прикладной обработки [8, 10]. Оно соответствует операторной модели DIP и позволяет менять отдельные части сценария.

Второе — описание интерфейса через контракт. OpenAPI даёт место, где можно связать адрес операции, параметры и ожидаемые данные [13]. Для реализации важно определить, какие возможности схем поддерживаются и как обрабатываются нарушения.

Третье — отдельное описание преобразований. JSONata подходит для согласования полей и вложенных структур JSON [4, 15]. При изменении сообщения можно проверить, достаточно ли исправить выражение, и сколько времени это занимает.

Практическая часть ВКР посвящена включению этих средств в сценарии DIP, совместимости со старыми интеграциями и выбору настроек сервера под нагрузку.

## 3. Обзор и сравнение аналогов


### Прямые аналоги

**Apache Camel.** Позволяет описывать маршруты и HTTP-операции, в том числе через OpenAPI, и преобразовывать данные, например через JSONata. Он покрывает многие задачи исследуемого HTTP-модуля [16].

**Mule с APIkit и DataWeave.** APIkit связывает контракт с обработчиками и проверкой входящих данных. DataWeave отвечает за преобразование сообщений. Это близкий пример объединения функций, которые нужны в нашем модуле [17].

### Косвенные аналоги

**Spring Integration.** Предоставляет HTTP-шлюзы, каналы и обработчики сообщений для сборки интеграционного приложения на Spring [18].

**Apache NiFi.** Обработка строится как визуальный поток процессоров. Для HTTP есть отдельные процессоры запроса и ответа, поддерживается multipart. Сходство с DIP — в сборке обработки из готовых элементов; в сравнении важно посмотреть, как запрос сохраняет связь со своим ответом [19].

Camel и Mule рассматриваю как прямые аналоги по набору интеграционных задач. Spring Integration и NiFi — как альтернативные способы построить такую обработку. Для всех четырёх решений отдельно возникает вопрос связи с существующими сценариями DIP.

## 4. Итоги

**Итоговая тема ВКР:** «Разработка и исследование HTTP-подсистемы сервисной шины ESB в платформе Data Integrator».

**УДК для тезиса:** **004.75 — распределённые системы обработки данных**. Рубрика соответствует межсистемному взаимодействию и распределённой обработке; её наименование приведено в [UDC Summary](https://finto.fi/udcs/se/page/014261?clang=en).

**Ключевые слова:** интеграция информационных систем; ESB; Data Integrator; Nexign BSS; HTTP; Undertow; OpenAPI; маршрутизация; валидация; JSONata; декларативная конфигурация; обратная совместимость.

### Актуальность исследования

Задача возникла в ходе разработки по заказу Nexign BSS. Data Integrator уже используется как платформа обработки данных; развитие HTTP-взаимодействия позволяет подключать к сценариям другие приложения [6, 7]. При этом у разных интеграций повторяются приём запроса, проверка, преобразование и подготовка ответа.

Если эти операции каждый раз разрабатывать отдельно, изменение контракта затрагивает несколько участков кода. Общие операторы и единое описание API дают возможность повторно использовать сделанную работу. Для заказчика это важно с двух сторон: затрат на разработку и времени, за которое можно выпустить нужное изменение.

В ВКР я проверю пользу подхода на типовых задачах, учитывая время разработки, совместимость существующих сценариев и нагрузку на сервер.

### Объект и предмет исследования

**Объект исследования:** взаимодействие корпоративных информационных систем по HTTP.

**Предмет исследования:** организация приёма, маршрутизации, проверки и преобразования HTTP-сообщений в Data Integrator, а также влияние этих механизмов на трудозатраты и время изменения интеграций.

### Цель исследования

Разработать и исследовать HTTP-подсистему ESB в Data Integrator, чтобы снизить затраты на создание и сопровождение интеграций и сократить время доставки изменений за счёт стандартных контрактов, готовых операторов и настраиваемых преобразований.

### Исследовательский вопрос и гипотеза

**Исследовательский вопрос:** сколько работы позволяет сэкономить использование HTTP-операторов DIP при создании интеграции и изменении её интерфейса?

**Гипотеза:** готовые механизмы и описание API через OpenAPI уменьшают время разработки и проверки, особенно при изменении существующего интерфейса. Это проверяется на одинаковых задачах с индивидуальной реализацией и с модулем ESB.

### Задачи исследования

1. Разобрать требования Nexign BSS, литературу и существующие средства HTTP-интеграции.
2. Описать путь запроса через HTTP Server, Gateway, Function Start, прикладной сценарий и ответ; определить, как между ними передаётся контекст.
3. Рассмотреть реализацию сервера на Undertow: декодирование, параметры, заголовки, cookies и приём файлов.
4. Разобрать загрузку маршрутов из OpenAPI/YAML, извлечение path-параметров, проверку типов и выбор responseStatus и responseContentType по умолчанию.
5. Рассмотреть преобразование структуры сообщения через JSONata и скрипты Groovy.
6. Описать HTTP Response и HTTP Error Response: кодирование, файлы, заголовки, cookies, серверные шаблоны и ответы для разных HTTP-кодов.
7. Проверить работу прежних сценариев, включая повторяющиеся значения и HTTP Response без Gateway и Function Start.
8. Подготовить автоматизированные проверки каждого HTTP-оператора и сравнить трудозатраты на контрольные изменения.
9. Провести нагрузочные испытания и определить, как настройки Undertow и сложность сценария влияют на результат.
10. Подготовить документацию операторов, рекомендации по сайзингу и выводы по исследованию.

### Как будет построен диплом

1. **Задача интеграции и обзор решений.** Объясню, зачем HTTP-функциональность нужна Data Integrator и заказчику, рассмотрю литературу и аналоги.
2. **Требования к модулю.** Опишу поддерживаемые данные, поведение операторов, ошибки, значения по умолчанию и совместимость.
3. **Архитектура и реализация.** Прослежу один запрос от Undertow до ответа, покажу связь с пакетами DIP, маршрутизацией и преобразованиями.
4. **Функциональные проверки.** Разберу тесты операторов, ошибочные запросы и проверки прежних сценариев.
5. **Эксперименты.** Сравню выполнение контрольных изменений и исследую HTTP-обработку под нагрузкой.
6. **Результаты применения.** Сформулирую рекомендации по настройке, документации и ресурсам, укажу ограничения решения.

Моя роль в проекте — участие в командной разработке. В дипломе я буду объяснять реализацию HTTP-части и её оценку; конкретные изменения кода свяжу с соответствующими рабочими задачами.

### Методы исследования

Работа включает анализ литературы и кода, сравнение аналогов, функциональные проверки и два вида экспериментов: внесение изменений в интеграцию и испытания под нагрузкой.

**Проверка поведения операторов.** Для каждого компонента нужны обычные и ошибочные входные данные.

| Компонент | Что проверяется |
|---|---|
| HTTP Server | Тело запроса и Content-Type, query, headers, cookies, multipart и файлы; повторяющиеся значения и ограничения размеров |
| HTTP API Gateway | Метод и путь, path-параметры, ограничения query/path, типы данных, отсутствие маршрута и настройки ответа по умолчанию |
| HTTP Function Start | Вход HTTP-пакета в нужный сценарий и доступность контекста; обработка неподходящего входного пакета |
| HTTP Response | Кодирование, статус, Content-Type, заголовки, cookies и выдача файла; работа с Gateway/Function Start и без них |
| HTTP Error Response и шаблоны | Выбор ответа для HTTP-кода, подстановка данных в шаблон и фактическое содержимое ответа клиента |

По исходному требованию прежде использовалось последнее из повторяющихся значений. В просмотренном коде колонки пакета получают первое значение, а метаданные сохраняют список. В регрессионном наборе нужно сравнить прежнюю и исследуемую версии отдельно для колонок и метаданных.

Для преобразований нужны примеры с вложенными объектами, массивами из нуля, одного и нескольких элементов, отсутствующими полями и разными типами. Результат сравнивается с заранее подготовленной структурой.

**Трудозатраты и доставка изменений.** Одну и ту же интеграцию нужно выполнить двумя способами: с индивидуально написанной HTTP-обработкой на Java и с использованием операторов ESB в DIP. Затем в обе версии вносятся одинаковые изменения:

- добавить параметр и ограничение для него;
- изменить имя и расположение поля в сообщении;
- добавить маршрут;
- изменить формат ответа об ошибке.

| Показатель | Как получить значение |
|---|---|
| Трудозатраты | Записать активное время настройки, программирования, тестирования и исправлений |
| Срок выполнения изменения | Зафиксировать начало согласованного задания и момент прохождения проверок на стенде |
| Доставка после коммита | Измерить время от фиксации изменения до успешного развёртывания на стенде |
| Объём правок | Посчитать изменённые файлы и строки кода/конфигурации; сопоставить с фактическим временем работы |
| Ошибки | Записать обнаруженные нарушения и время их исправления |

В DORA время доставки изменения относится к пути от коммита до production [20]. В этой работе сначала измеряется доставка на тестовый стенд; область измерения будет указана вместе с результатами.

Экономию трудозатрат можно выразить как **(Tбаз − TESB) / Tбаз × 100 %**, где Tбаз > 0. Если вариант с ESB потребует больше времени, результат будет отрицательным. Для денежной оценки нужны ставки и затраты на инфраструктуру; без этих данных сравнение проводится в человеко-часах.

Затраты на модуль учитываются отдельно от затрат на очередную интеграцию, с учётом ожидаемого числа таких задач. Фиксируются опыт исполнителя и порядок заданий, поскольку повторное выполнение ускоряет работу.

**Нагрузка и сайзинг.** В Apache JMeter [22] подготавливаются запросы для четырёх сценариев: маршрутизация с простым ответом, проверка данных, преобразование структуры и передача файла. Для каждого сценария изменяются размер сообщения и число одновременно выполняемых запросов. Затем проверяются разные настройки потоков Undertow.

Измеряются успешно обработанные запросы в секунду, задержки p50/p95/p99, ошибки, CPU и память. Перед замером JVM прогревается; каждое условие повторяется не менее трёх раз. Фиксируются версии, ресурсы стенда, настройки сервера и состав сценария.

По этим результатам можно будет объяснить, при какой нагрузке требуется менять настройки или добавлять ресурсы. Для файловой обработки отдельно важно проследить расход памяти при увеличении размера запроса.
